## Correction (final whole-branch review): the GPU session's throughput and correctness-gate numbers below are WITHDRAWN

This doc originally reported both correctness gates as passed and
carried the session's throughput numbers as this phase's headline
result. The phase's final whole-branch review found that neither claim
holds up, for a structural reason, not a measurement fluke. Stated
plainly, the way this project's own practice ("never quote a benchmark
number that wasn't measured," "a kernel that's fast because it's
silently wrong is a bug, not a result") demands:

- **The session's own baseline (`--drafter none`) generated a degenerate
  output**: 64 repetitions of token id `0`, for all 4 test prompts. This
  is not a plausible real continuation of "The quick brown fox jumps over
  the lazy dog.", "def fibonacci(n):", or either of the other two
  prompts -- something in the chain produced garbage.
- **Both correctness gates "passed" only because they matched this same
  degenerate baseline** at k=4 and k=8, where the drafters also produced
  all-zeros. Two broken outputs agreeing with each other proves nothing
  about correctness -- the "GPU correctness gates: both passed" section
  below documents a vacuous pass, not a real one.
- **The k=1/k=2 sweep runs -- the only runs this session produced
  plausible, varied, non-degenerate tokens on -- were never checked
  against the baseline at all.** The runbook's own k-sweep design
  (step 12) explicitly skipped `--compare-generated-tokens` at every k
  but 4, reasoning that correctness doesn't depend on k. That reasoning
  is correct in principle but irrelevant here: it assumes the k=4 gate
  was a real correctness check, and it wasn't. The actual scope of how
  far the k=1/k=2 outputs diverge from true plain-greedy decoding is
  unknown.
- **Why the gate could not have caught this even in principle**: the
  baseline was generated by `speculative_generate` -> `run_speculative_rounds`
  itself, called with `drafter=None` -- the exact same shared
  propose/verify/accept/rollback loop the gate exists to check. A gate
  that compares code against itself can never catch a bug that lives in
  that shared code, which is exactly where this branch's own real
  EOS-boundary bug lived earlier in development (fixed in commit
  `8c0c883`). This is finding C2 of the final review.

**Therefore: the throughput numbers (+21.8% for draft-model, +76.9% for
prompt-lookup), every cost-per-1M-token figure derived from them, and
every k-sweep number below are WITHDRAWN.** They are not this phase's
headline result. The tables are kept below, relabeled, for the historical
record and because the *environment* and *memory* findings alongside them
are still accurate -- but none of the throughput/acceptance numbers
should be cited or reused until a future session re-measures them
honestly.

**What now backs the algorithm's own correctness** (not the GPU session):
extensive hand-verified CPU-only tests in `test_decode.py` and
`test_drafters.py` (toy models with closed-form expected continuations,
still all passing); a genuinely independent CPU-level oracle test added
by the fix wave that produced this correction
(`plain_greedy_generate` in `src/dispatch/speculative/decode.py`, sharing
no code with `run_speculative_rounds`, so it can actually catch a bug in
the shared loop rather than agreeing with it); and a new real-model,
real-tokenizer, real-`transformers.Cache` end-to-end test of
`DraftModelDrafter` running inside `run_speculative_rounds`
(`test_speculative_generate_with_draft_model_drafter_matches_plain_greedy_decode`
in `test_decode.py`), closing a gap where that exact combination had
never been exercised outside the now-discredited GPU gate. All of this
is CPU-only, deterministic, and reproducible without spending GPU money.

**What would be needed for a trustworthy GPU-measured result**, none of
which is this fix wave's job to do:

1. The oracle-independence fix itself -- **done**, described above.
2. **Root-causing why the GPU session's baseline degenerated in the first
   place -- NOT done.** This needs a new rented GPU session (real money)
   and is explicitly out of scope for a docs/code review-fix pass; it is
   a decision for the project owner, not something to guess at from a
   laptop. (A real bug in the shared verify/accept/reject loop is one
   candidate explanation, given C2 above means it was never actually
   ruled out -- but that is a hypothesis, not a finding.)
3. **A re-run with `--compare-generated-tokens` checked at every k-sweep
   point**, not just the k=4 gate (finding I5 of the final review) --
   also not done here.

Everything below this point is the original run account, with the
sections that reported now-withdrawn numbers relabeled accordingly. The
environment, memory-checkpoint, and cost-tracking sections are unaffected
by this correction -- they describe real dollars spent and real memory
allocated, not token correctness, and remain accurate as originally
written.

## Environment

under `transformers==5.17.0` (this repo's pinned floor), all from the
remote code targeting an older `transformers` API surface:
`is_torch_fx_available` removed, `DynamicCache.get_usable_length`

depend on, and downgrading would have silently broken that. All five
fixes are a pod-local, never-committed monkeypatch, folded into the
runbook. Full account in the runbook; not repeated here.

Sources: the 8 `2026-09-17-phase-5b-k-sweep-{draft-model,prompt-lookup}-{1,2,4,8}-results.json`
files. Per the runbook, this sweep intentionally omitted
`--compare-generated-tokens`, reasoning at the time that "the gate above
already proved exact-match correctness at k=4, and correctness does not
depend on `k`." **That reasoning turned out to rest on a false premise --
the k=4 gate had not actually proved correctness (see the correction at
the top of this doc) -- which is exactly why item 2 below, found by
reading the raw token files rather than trusting the gate, is the
finding that this doc's final review escalated into the withdrawal
above.** This is finding I5 of that review: a re-run should check
`--compare-generated-tokens` at every k, not just k=4.

**Two things worth flagging plainly, found only by reading the
generated-token JSON files directly (not just the results JSONs) -- item
2 here is, in hindsight, the first real evidence of the problem this
doc's correction describes:**

1. **The k=4 point measured twice in this session doesn't repeat
   exactly.** The gate run's own k=4 throughput for draft-model is 26.667
   tok/s (`2026-09-17-phase-5b-draft-model-results.json`); the k-sweep's
   independent k=4 run of the same config measured 29.150 tok/s
   (`2026-09-17-phase-5b-k-sweep-draft-model-4-results.json`) -- a ~9%
   difference between two nominally identical configurations run at
   different points in the same session. Prompt-lookup shows the same
   pattern (38.733 vs. 40.385 tok/s, ~4%). Both are real, measured
   numbers from separate process invocations; the difference is reported
   as run-to-run variance rather than reconciled into one number, since
   nothing in either results JSON explains it and inventing an
   explanation would be exactly the kind of "helpfully adjusted" number
   this project's practice rules out.
2. **The actual generated token content is not the same generation
   problem at every k.** Reading `*-generated-tokens.json` directly: the
   plain baseline's own greedy continuation (`2026-09-17-phase-5b-baseline-generated-tokens.json`)
   for all 4 prompts is 64 repetitions of token id `0` -- and both k=4
   correctness-gate runs reproduce that exactly (which is why
   `token_match` is `true`; this is a genuine, verified match, not a
   coincidence). The k=4 and k=8 sweep runs also reproduce all-`0`
   output for all 4 prompts. But the k=1 and k=2 sweep runs do not: both
   drafters' k=1/k=2 generated-token files contain varied, non-degenerate
   token sequences that differ from the baseline's all-`0` trajectory
   *and* from each other (e.g. draft-model k=1's prompt 0 uses token ids
   `{13, 15, 16, 17, 185, 207, 398, 690, 992, 14166, 14594, 24962}`;
   prompt-lookup k=1's prompt 0 uses a different set entirely). Since
   speculative decoding's exactness guarantee means every `k` should
   reduce to the identical greedy trajectory as the plain baseline, this
   is a real discrepancy in what the k=1/k=2 sweep points are actually
   measuring -- and the runbook's own k-sweep design (step 12) explicitly
   chose not to check `--compare-generated-tokens` at any k but 4, so
   this was never caught in-session. Reported here as an open
   observation, not a root-caused bug (that would need code changes and
   further GPU time, out of this docs-only task's scope) -- likely
   explanation is floating-point non-associativity between the batched
   verification forward pass (processing k+1 tokens at once) and the
   one-token-at-a-time baseline path, which would only matter if the
   model's real logits are frequently near-tied at this point in
   decoding (consistent with the all-`0` degenerate collapse seen at
   k=4/k=8). Worth a follow-up investigation before treating the k=1/k=2
   sweep points as a clean apples-to-apples comparison with k=4.

## Risk verdicts (design doc section 8) -- WITHDRAWN, rest entirely on the numbers above

**See the correction at the top of this doc.** Both verdicts below were
written as settled conclusions from the measured run and k-sweep; both
inherit those tables' unreliability in full and should be read as "what
this session appeared to show," not as established results. They are
kept verbatim because Risk 2's own text turned out to contain the first
documented sighting of the degenerate all-`0` collapse -- at the time
written, interpreted as a property of the model, not (as the final
review now flags as the live, unruled-out hypothesis) a possible bug in
the shared loop these verdicts' own numbers came from.

**Risk 1: "the 7B draft may not be meaningfully cheaper than the target
... net speedup could be small or negative once the draft's own cost is
counted."** Partially materialized, reported as measured rather than
smoothed into a clean yes/no. The draft-model drafter's net speedup over
baseline is real and positive: **+21.8%** at k=4 (26.668 vs. 21.897
tok/s), so the risk's worst case (a negative or negligible speedup) did
not happen. But the risk's underlying concern -- that the dense 7B
draft's own cost would eat into the win -- shows up clearly in a
different place than the risk anticipated: **draft-model is not the
fastest option measured.** Prompt-lookup, a free (no second model)
drafter, beats it substantially (+76.9% vs. +21.8% over baseline),
despite draft-model accepting its own proposals **91.9%** of the time
against prompt-lookup's **22.1%** -- more than 4x higher acceptance. The
7B draft's near-doubling of TTFT (0.233s vs. baseline's 0.093s and
prompt-lookup's 0.098s) is the direct cost the design doc named, and it
is large enough that a much-more-accurate drafter still loses the raw
throughput race to a much-less-accurate, free one. This is exactly the
kind of finding this project's practice keeps rather than buries: high
acceptance is not sufficient by itself, and this session's own numbers
show that plainly on real hardware.

**Risk 2: "prompt-lookup may show near-zero acceptance even with the
added 4th prompt, if that prompt doesn't repeat as cleanly as intended."**
Did not materialize as stated, but for a more surprising reason than the
design doc anticipated. Prompt-lookup's acceptance rate at k=4 is
**22.1%**, not near-zero, and both correctness gates confirm this rate
comes from real, verified matches (`token_match: true` for all 4
prompts including `prompt_003_tokens`, the repetition-heavy prompt).
However, reading the generated-token files directly shows *why*
acceptance is non-trivial is not what the design intended: **at k=4, all
four prompts' actual greedy continuations under this quantized model
collapse into repeating a single token (id `0`) for the full 64-token
window** -- not just the purpose-built repetition prompt. This makes
every prompt maximally, trivially repetitive at the token level by k=4,
which is an easy target for n-gram lookback regardless of whether the
*prompt's own text* was designed to repeat. The results JSONs report
only an aggregate acceptance rate across all 4 prompts, not a per-prompt
breakdown, so this finding cannot confirm whether the repetition-heavy
prompt specifically contributed more matches than the other three within
that 22.1% -- only that all 4 prompts' real generated content was, in
practice, equally repetitive at k=4. The risk as framed (the 4th prompt
failing to repeat "as intended") is moot: the model's own degenerate
greedy behavior overtook the experimental design's premise. Whether this
all-`0` collapse is itself specific to the quantized kernel, this exact
prompt set, or greedy decoding at this length in general was not
investigated further -- out of scope for this docs-only task, flagged as
a candidate follow-up.

## Summary (rewritten by the final whole-branch review)

**This session's own throughput and correctness-gate claims are
withdrawn.** The GPU session's baseline (`--drafter none`) produced a
degenerate output -- 64 repetitions of token id `0` for all 4 test
prompts, not a plausible continuation of any of them. Both correctness
gates "passed" only because they matched that same degenerate output at
k=4/k=8, which proves nothing: two broken outputs agreeing is not
correctness. The k=1/k=2 sweep runs, the only runs that produced varied,
plausible tokens, were never checked against the baseline. The root
structural reason this could happen at all -- the baseline was generated
by the very code the gates exist to check -- is finding C2 of the final
review; the missing per-k comparison is finding I5. Every throughput
number, acceptance rate, and derived cost-per-1M-token figure above is
unreliable and should not be cited.

**What is real and unaffected**: the session spent $0.6833 of its $10
cap (a real dollar figure, not a correctness claim); the memory
checkpoints (16.75GB target-only, 29.62GB target-plus-draft-model) are
real allocator readings, not token-correctness-dependent; the five
`transformers` environment fixes in the Environment section above were
real, necessary, and are unrelated to this correction.

**What now backs the algorithm's own correctness**, put in place by the
fix wave that produced this correction: a genuinely independent CPU-level
oracle (`plain_greedy_generate`, sharing no code with
`run_speculative_rounds`) now backs the `--drafter none` baseline path in
`scripts/run_speculative_bench.py` itself, closing the structural gap
finding C2 identified; runtime cache-lag assertions in both
`run_speculative_rounds` and `DraftModelDrafter.propose` turn a future
silent cache-desync into a loud crash instead of plausible-looking
garbage; and a new real-model, real-tokenizer, real-`transformers.Cache`
end-to-end test exercises `DraftModelDrafter` inside the full loop for
the first time outside the now-discredited GPU gate, and passes. All of
this is CPU-only, deterministic, and already in `make check`.

**What is still open, and explicitly not this fix wave's job**:
root-causing why the GPU session's baseline degenerated in the first
place needs a new rented GPU session and is a decision for the project
owner, not a docs/code review-fix task; a trustworthy throughput number
for Phase 5b needs that root-cause work done first, then a re-run with
`--compare-generated-tokens` checked at every k-sweep point, not just
k=4. Until that happens, Phase 5b's algorithm and code are done and
covered by CPU-level tests, but its GPU-measured performance claims are
not established.
